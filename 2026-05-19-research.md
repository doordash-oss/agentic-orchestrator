# Research: `feature/markdown-review-rendered` branch

## Research Question

> Understand what this branch is implementing.
>
> Question after that: Instead of flipping with Ctrl+P back and forth from preview to "raw", is there a way to show the unrendered view "row by row" as the cursor moves to a specific row? This way, the edit and the preview can coexist in a single pane.

## Summary

The branch adds a **second rendering mode to the artifact-review screen**: every time a reviewer opens a Markdown artifact (`.md` / `.markdown`) — for plan / gate / rewind reviews — the editor panel now opens in a **rendered Glamour preview** instead of the raw source. The reviewer can swap to the source editor with `Ctrl+P` and back to the preview with `Ctrl+P`. Edits made in the source view are reflected in the preview *from the in‑memory editor buffer*, not from disk (with explicit save points wired in along all transitions). Non‑markdown artifacts continue to open directly in the source editor.

The work was delivered in four commits, all on the file `internal/tui/artifact_review.go`, the helper `internal/tui/markdown_renderer.go`, and the existing `internal/tui/markdown` package:

| Commit | Title | What it adds |
| --- | --- | --- |
| `655bcb5` | Phase 1/4 — tracer‑bullet | Adds the second preview viewport + `Ctrl+P` toggle scaffolding. |
| `8709380` | Phase 2/4 — preview workflow parity | Opens markdown reviews in preview by default; restores scroll, save points, dirty‑state titles, footers, narrow‑layout chrome. |
| `83c645d` | Phase 3/4 — buffer truth & edit sync | Preview renders the *unsaved* editor buffer (single source of truth) and re‑renders on every Update tick. |
| `5b71037` | Phase 4/4 — resilience, layout, verification | Renderer panic / empty‑string / malformed‑markdown fallback to plain text; size recalculation; ~570 lines of TUI tests added. |

Those are mechanical edits and not part of the markdown‑preview feature itself.

## Detailed Findings

### 1. The two-mode artifact review model

`internal/tui/artifact_review.go:50-141` (`ArtifactReviewModel`)

The model now carries both panes side by side:

- `editor MarkdownEditor` — the raw, vim‑like source editor.
- `previewViewport viewport.Model` — a scrolling viewport that holds the Glamour‑rendered Markdown.
- `documentMode artifactDocumentMode` — an enum (`artifactDocumentRaw=0`, `artifactDocumentPreview=1`) that decides which one is currently visible.

Both panes always exist; only one is rendered at a time. The preview viewport is constructed at `NewArtifactReviewModel` (line 204) by `newArtifactPreviewViewport` (lines 227‑238) with `SoftWrap = true`, `FillHeight = true`, and a restricted KeyMap (`up`, `down`, `k`, `j`, `pgup`, `pgdown`) so chat-style keys can't accidentally scroll it.

The default mode is set in the constructor (`artifact_review.go:209-212`):

```go
if isMarkdownReviewArtifact(artifactPath) {
    m.documentMode = artifactDocumentPreview
    m.refreshPreviewContent()
}
```

`isMarkdownReviewArtifact` (lines 240‑247) gates on `.md`/`.markdown` extensions; `supportsRenderedPreview` (lines 249‑251) also gates out the need‑user‑input questionnaire mode.

### 2. The `Ctrl+P` toggle

`artifact_review.go:393-396` routes the key, and `toggleDocumentMode` (lines 455‑466) flips `documentMode` and re-renders the preview if entering preview mode. Cursor / editor mode (NORMAL vs INSERT) is **not** disturbed by the toggle — only the visible pane changes (verified in `artifact_review_test.go:187-240`).

### 3. Preview content source: the live editor buffer (not the file on disk)

`artifact_review.go:253-259`:

```go
func (m *ArtifactReviewModel) refreshPreviewContent() {
    if !m.supportsRenderedPreview() { return }
    width := max(m.previewViewport.Width(), m.editorContentWidth())
    m.previewViewport.SetContent(renderMarkdownPreview(m.editor.Content(), width))
}
```

This is the Phase 3 "buffer truth" decision: even with unsaved edits, the preview renders `m.editor.Content()`, not `os.ReadFile(artifactPath)`. The test `TestArtifactReview_RenderedPreviewUsesUnsavedEditorBuffer` (`artifact_review_test.go:242-282`) locks this in — it inserts a `!` in raw INSERT mode, toggles to preview without saving, and asserts the preview shows the unsaved text while the file on disk is untouched.

`refreshPreviewContent` is called on (a) `WindowSizeMsg` (line 279), (b) every key press while in preview mode (line 469), and (c) at every `renderDocumentContent` (line 1254) so each redraw is up‑to‑date with the editor buffer.

### 4. The Markdown renderer pipeline

`internal/tui/markdown_renderer.go` defines a `markdownRenderer` function type and a package‑level `renderMarkdown` variable that defaults to a plain `lipgloss.NewStyle().Width(width).Render(text)`. `SetMarkdownRenderer` (called from the app binary outside the `tui` package) swaps in the Glamour renderer:

`internal/tui/markdown/markdown.go:50-71` — `Render`:
- clamps width to `minWidth = 20`,
- uses a per‑width memoization (`cache` map) so re‑renders on resize/scroll are O(1),
- builds one `glamour.TermRenderer` per width (kept in `renderers` map under `renderersMu`),
- falls back to plain lipgloss wrapping on any error or empty output.

`renderMarkdownPreview` (`markdown_renderer.go:38-51`) wraps that with a `recover()` and a "rendered to whitespace" guard, so a panic or a degenerate empty render falls through to `renderPlainMarkdownPreview`. The tests `TestArtifactReview_MalformedPreviewFallbackKeepsPlainText` and `TestArtifactReview_RendererPanicFallsBackToPlainText` (`artifact_review_test.go:284-337`) cover both paths.

### 5. Save points: every transition out of an "edit‑bearing" surface flushes

Implicit saves were added wherever a user can leave the editor in a state that would otherwise be lost or confused:

- `Ctrl+D` / `Ctrl+]` / `Esc` opening the action menu (`artifact_review.go:397-411`, `437-444`).
- `Tab` to chat (`toggleFocus`, lines 530‑532).
- Agent about to write to the file (`detectAgentEdit`, lines 811‑830 — saves user edits first, then lets the agent's Edit/Write tool overwrite the file, then `reloadAfterAgentEdit` pulls the new content back in and re-marks the buffer clean).

`Ctrl+P` itself does **not** save — the buffer is single‑source‑of‑truth, so toggling between preview and source is free.

### 6. Title and footer chrome

`documentTitle` and `documentTitleForWidth` (`artifact_review.go:1258-1317`) produce:

- `<file> [Rendered preview] [+] [agent edits pending]` in preview mode (or short form `Preview +` for narrow widths),
- `<file> [Source NORMAL] [+]` / `[Source INSERT] [+]` in raw mode (or `Src NORM +` / `Src INS +` narrow),

with `[+]` indicating dirty and `[agent edits pending]` indicating un‑accepted green‑highlighted lines.

`renderFooter` / `compactFooterHints` (lines 1387‑1478) produce keybinding hints:

- preview footer: `Preview │ Ctrl+U/F: scroll │ Ctrl+P: raw`
- raw footer: `Raw │ Ctrl+P: preview │ i: insert │ Ctrl+U/F: scroll`
- chat focused footer mentions whichever side it would Tab back to (`Tab: preview` or `Tab: editor`).

`TestArtifactReview_NarrowLayoutKeepsChromeWithinWidth` (`artifact_review_test.go:488-499`) checks the narrow versions stay within terminal width.

### 7. Editor layout still recomputes the preview pane

`recalcLayout` (`artifact_review.go:1178-1190`) sets the editor *and* `previewViewport` to the same content width / editor height every time the layout changes. `editorHeight` shrinks when chat is focused (~30 % of the screen, floor `chatPanelExpandedH=12`, with a minimum editor height of 8 rows enforced — lines 1152‑1171).

### 8. The raw `MarkdownEditor` (unchanged surface, important context)

`internal/tui/markdown_editor.go` is the vim-like editor on the raw side: it stores `lines []string` and tracks the cursor as `(row, col)` in runes (`markdown_editor.go:47-67`). Visible/soft‑wrap math lives in `visualRowCount` / `ensureVisible` (lines 675‑701) and `View` (lines 834‑990), the latter renders line numbers, per‑line markdown syntax coloring (`renderLine`, lines 759‑798), agent-edit green highlighting (`highlightedLines`, lines 839 + 926‑956), and the cursor.

The editor does *not* publish a "current row → rendered span" mapping — its only awareness of the rendered preview is via the `documentMode` flag.

## Architecture Documentation

- **Single-source-of-truth buffer.** `MarkdownEditor.Content()` is what the preview, the agent's `Edit` tool, and the on-disk file all align to at every save point. The viewport never reads the file directly.
- **Pluggable renderer.** `markdownRenderer` is a function variable so the lightweight `internal/tui` package tests don't pull in Glamour/chroma. The app binary calls `SetMarkdownRenderer(markdown.Render)` to wire in the real one.
- **Defensive rendering.** `renderMarkdownPreview` is wrapped in a `defer recover()` and a "stripped output is empty" guard. The cache lives one layer below (`markdown.Render`) and is keyed by `(text, width)`.
- **Layered key handling.** Key routing order is: action menu overlay → need-user-input form → permission prompt → global hotkeys (`Ctrl+P`, `Ctrl+D`, `Tab`, `Ctrl+Y/Z`, `Esc`) → chat-focused branch → preview viewport branch (when in preview) → editor (default). Tests assert this routing (e.g. `Ctrl+P` in INSERT mode toggles the pane instead of inserting `p`).

## Answer to the follow-up question: "row-by-row inline preview as the cursor moves"

**Short answer: yes, this is achievable, but only as a hybrid; there is no clean way to keep Glamour rendering everywhere and inline‑swap only the cursor row.** The cleanest implementation today would render the *line containing the cursor* (and any line that is part of the same Markdown block) as raw source and the rest as Glamour output, joined together in a single viewport.

The reason it can't be a literal "show row N as raw, all other rows as rendered":

- `markdown/markdown.go` calls `glamour.TermRenderer.Render(text)` on the whole document — Glamour emits ANSI block by block (heading, paragraph, list, fenced code, blockquote), wraps to the requested width, and does **not** publish a source‑line → output‑line map. So you can't reliably ask "which output rows came from source row N?" after the fact.
- Many constructs are inherently multi‑line: a fenced code block, a list item that wraps, a setext heading (`===` / `---` underline), a table row. Replacing just the cursor's source line with raw text would split those blocks.

What you *can* do with the existing pieces:

1. **Block‑level swap.** Compute the Markdown block the cursor is inside (e.g. by walking from the cursor row outward until you hit a blank line / a different block type). Render the document *above* and *below* that block with Glamour, render the block itself as raw source, and concatenate. This gives a single pane where the active block is editable while everything else stays styled. Keeps Glamour intact for the other blocks; cost is one extra Glamour render per cursor move (cheap because the `(text,width)` cache in `markdown/cache.go` will hit on the unchanged halves).
2. **Per‑line swap with no Glamour for the active line.** A simpler variant: replace just `lines[cursor.row]` with the raw source line and render the *rest* through Glamour. Works fine for paragraphs but degrades for multi-line constructs (code fences, tables, blockquotes spanning lines).
3. **Fully line-by-line markdown.** Use the existing per-line `renderLine` in `markdown_editor.go:759-798` (which already does headings/bullets/inline‑bold/italic/code) instead of Glamour for the whole document, and run the cursor row unstyled. This is the most uniform and gives you guaranteed source‑line ↔ rendered‑line alignment — at the cost of losing Glamour's block‑level styling (boxed code blocks, tables, link styling).

The main trade-off is therefore **block fidelity vs. row mapping**: Glamour gives the prettiest output but no per-row alignment, while the editor's per-line renderer aligns 1:1 with cursor rows but is visually simpler. If you want this, I'd recommend option (1) — block‑level swap — wired into `refreshPreviewContent` and re-triggered on every cursor move; it preserves the current preview's look-and-feel and only sacrifices styling on the block the user is actively editing.
